Implementation and verification status
======================================

This page separates *what exists* from *what has been shown to work*. A component is described
by the highest verification level it has reached, using these levels (each includes the
ones before it):

.. list-table::
   :header-rows: 1
   :widths: 24 76

   * - Level
     - Meaning
   * - Implemented
     - The functionality exists in the repository.
   * - Unit-tested
     - It has passing isolated tests.
   * - Integration-tested
     - Components have been tested together.
   * - Core-verified
     - The integration has been tested against the actual ``polynomial_cl`` package (never a
       stand-in), installed from the pinned commit.
   * - Real-data-verified
     - Executed against the actual MNIST archives.
   * - Reproducibility-verified
     - A result has been independently reproduced.
   * - Publication-ready
     - The evidence and analysis support the claims of the associated paper.

Nothing in this repository is currently *publication-ready*.

How these statements were obtained
----------------------------------

Everything below marked as verified was executed for this documentation, on 2026-11-05, in a
fresh virtual environment (Linux, Python 3.12.3, NumPy 2.5.4) created with
``pip install -e ".[dev]"``, so that the core was installed from the pin in ``pyproject.toml``
(at that time core commit ``f90eac9``, the merge commit of the core's ``continual``/``data``
refactor on its ``main``, dated 2026-11-05; the page previously named ``4d7e692`` here, which is
a later commit, dated 2026-11-08, and cannot have been the pin on 2026-11-05).

.. list-table::
   :header-rows: 1
   :widths: 46 54

   * - Command
     - Result
   * - ``BENCH_REQUIRE_CORE=1 BENCH_REQUIRE_PINNED_CORE=1 pytest -q``
       (single-threaded BLAS)
     - 293 passed, 3 skipped (the skipped tests are the opt-in real-data tests below)
   * - ``python -m polynomial_cl_bench.verify_data --data-dir <mnist dir>``
     - all four archives match the protocol's sha256 hashes
   * - ``BENCH_SLOW=1 pytest tests/test_full_split_mnist.py`` (real MNIST, about 50 s;
       run with a local checkout of the core at the same commit)
     - 3 passed
   * - ``python -m polynomial_cl_bench.runner --spec configs/experiment_polynomial_reference.json
       --data-dir <mnist dir> --out <dir> --reproduce-check`` (5 seeds)
     - 5 completed, 0 failed, integrity passed; reproducibility check for seed 0:
       exact match, maximum absolute difference 0.0; ``--resume`` into the same directory
       succeeded
   * - ``ruff check .`` and ``ruff format --check .``
     - clean

The reference run reported mean final accuracy 0.6751 (sample standard deviation 0.0038 over
5 seeds) and mean forgetting 0.0734, with a wall time of about 23 s per run on the machine used.
These numbers describe a *reference configuration that was not tuned* (see
:doc:`algorithms`); they are quoted here as evidence that the pipeline runs, not as a result.
The run is correctly reported as *not publishable* by the benchmark itself.

That run used a core without the lean mode and timing split described in :doc:`algorithms`,
and its wall time is the time of that configuration. The polynomial adapter has since been
changed to use them when the core has them (``tests/test_lean_adapter.py``): the accuracy
matrix is unchanged, and the cost of a run is lower. The reference experiment's runtime is
therefore regenerated by the ``benchmark-results`` workflow rather than quoted here.

Re-check against newer core commits (2026-11-10)
-------------------------------------------------

The suite was re-run after the core moved on, in a separate environment (Linux, Python 3.12.3,
NumPy 2.5.4, single-threaded BLAS), with the core installed from a local clone at each commit
and the benchmark installed editable. Synthetic data only: the real-data tests, the
pinned-install check (``BENCH_REQUIRE_PINNED_CORE=1``) and the reproduction of the stored
records were not repeated.

.. list-table::
   :header-rows: 1

   * - Core commit
     - ``pytest -q`` result
   * - ``4d7e692`` (lean mode, timing split; diagnostics on by default)
     - 367 passed, 11 skipped (Sphinx not installed, so the documentation and paper build tests
       were skipped)
   * - ``2e806d7`` (diagnostics opt-in, whole-call timings)
     - 366 passed, 1 failed before the fix below (same environment as above); after the fix and
       with Sphinx installed, 375 passed, 4 skipped (the three opt-in real-MNIST tests and the
       pinned-install check)

The one failure was in the test harness, not the adapter: the test that imitates a core without
the ``diagnostics`` argument still called the new ``run_condition``, whose default changed.
The imitation now forces the full run an older core would have done. For four configurations
(``ordinary`` and ``ordinary_no_replay``, each with and without ``feature_power``) the accuracy
matrices produced through the adapter were bit-identical under ``4d7e692`` and ``2e806d7``.
The adapter now also raises if the core's record reports a ``diagnostics`` setting other than
the requested one.

Review of the workflow changes (diagnostics passed explicitly, ``pipefail``, a comparison
cache keyed by the benchmark commit, validated reuse of stored comparison records) added
twelve tests (387 passed, 4 skipped in total; each fix was checked to be caught by its test by
removing it). The workflows themselves have still **not been executed**; these tests check
their structure and the tools' logic only.

Comparability of the two algorithms
-----------------------------------

A comparison is reported publishable only if each algorithm's hyper-parameters came from a
validation-tuning result that is official-eligible **and** both results were produced by the
same selection procedure: the same selection rule and margin, the same selection seeds, the
same number of tuning runs and the same validation split. ``validate_experiment`` records a
publication blocker when any of these differs or was not recorded. Tuning results written
before this check existed lack the budget and validation-split fields, so a comparison built
from them is blocked until they are regenerated. The development-mode records in
``results/`` are in that position; they are also not official-eligible.

The ``diagnostics`` input of ``paper-results`` was removed: the study always passes the core's
``--diagnostics``, so the paper's statement that the study keeps diagnostics on cannot be made
false by a manual run. The analysis still reports a study whose files disagree on the setting.
